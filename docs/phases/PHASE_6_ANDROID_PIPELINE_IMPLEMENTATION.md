# Phase 6 (host side) — Android Behavioral Event Pipeline

## Overview

The Android Frida agent generated by `hook_installer.py` already hooked 24
Java-layer APIs across nine monitors (permissions, SMS, location, contacts,
clipboard, camera, microphone, accessibility, overlay) and emitted them to the
host in the same batch format as the Windows agent.

**None of those events survived arrival.** `HookEngine.ingest()` resolves every
incoming event through `resolve_api()`, and the catalog contained Windows APIs
only, so `resolve_api("SendSMS")` returned `None` and the call was dropped
before normalization:

```python
hook = resolve_api(raw_name)
if hook is None:
    return None, []          # every Android event landed here
```

The guest was collecting the evidence and the control plane was discarding it.
Nothing errored, nothing logged — the Android side of the dynamic analysis
simply produced no findings, no risk contribution and no MITRE mapping.

This phase closes that path: Android events now normalize, decode, correlate
into named behaviors, score, and reach the report through exactly the same
route the Win32 calls already took.

## Why it matters for this problem statement

The PS names light-bill fraud, loan-app scams and fake e-Challan/RTO schemes,
which on Android are almost entirely built from the capabilities that were
being dropped:

| Scam pattern | Behavior now detected |
|--------------|----------------------|
| Loan-app extortion | Contact list harvested, then messaged or uploaded |
| Fake e-Challan / bank fraud | OTP read from the inbox and forwarded |
| Banking trojan | Overlay drawn over the bank app when it comes to the front |
| Stalkerware | Continuous location polling, microphone and call recording |
| UPI/crypto theft | Clipboard payment address read and substituted |

## Implementation

### 1. `dynamic-sandbox/hooks/api_catalog.py`

- **`platform` field** on `ApiHook` (`"windows"` default, `"android"` for the
  new entries). CAPE hooks native exports and would reject Java class names, so
  the two guests must be separable.
- **10 new categories**: `PERMISSIONS`, `SMS`, `LOCATION`, `CONTACTS`,
  `CLIPBOARD`, `CAMERA`, `MICROPHONE`, `MEDIA_CAPTURE`, `ACCESSIBILITY`,
  `OVERLAY`.
- **24 Android hook entries**, each with captured arguments, baseline risk,
  rate limit, MITRE Mobile technique and the reason it is watched.
- **Android constants**: dangerous permissions, content-URI markers, window
  types and layout flags, accessibility event bitmask, audio/video sources,
  credential search terms.
- **Helpers**: `is_dangerous_permission`, `dangerous_permissions`,
  `classify_content_uri`, `is_overlay_window`, `is_covert_audio_source`,
  `has_credential_search_term`, `apis_by_platform`.
- **`ANDROID_REQUIRED_APIS`** — a startup guard. Every name the agent emits
  must resolve; a mismatch now raises at import instead of silently costing a
  capability.
- Alias generation (`NameA`/`NameW`) restricted to Windows entries.

### 2. `dynamic-sandbox/hooks/hook_engine.py`

- **13 Android condition predicates** — `dangerous_permission`, `sms_uri`,
  `contacts_uri`, `high_frequency_location`, `crypto_address_clipboard`,
  `covert_audio_source`, `camera_video_source`, `credential_search`,
  `text_capture_event`, `window_change_event`, `overlay_window`,
  `invisible_overlay`, `dynamic_dex` — plus `_as_int`/`_as_bool` coercion,
  because Frida reports longs as strings and flags as either bools or ints.
- **18 Android chain rules**, listed in `dynamic-sandbox/hooks/README.md`.
- **`_decode_android()`** — derived fields (window type name, audio source
  name, `records_call`, `content_family`, `high_frequency`, dangerous
  permission subset) computed once so rules, evidence and dashboard agree.
- **`_track_android_signals()`** — aggregates that a raw call count cannot
  express: how many accessibility events carried *typed text*, how many
  overlays were the *invisible* kind, how many bytes of audio were actually
  read, which packages were observed, which numbers were messaged.
- **8 Android volume findings** with thresholds set well above ordinary app
  behavior; counts come from `call_counts`/`android_signals` so a sample that
  floods a hook past its rate limit is still measured on what it did.
- **Evidence extraction** extended with SMS destinations, content URIs,
  observed packages, window type, audio source, permissions, credential
  searches and location interval.
- `summary()` now exposes `android_signals` and
  `android_permissions_requested`.

### 3. `dynamic-sandbox/hooks/hook_installer.py`

- `generate_cape_config()` filtered to Windows entries.
- `installation_manifest()` reports `windows_apis`/`windows_api_count` and
  `android_apis`/`android_api_count` separately, so a deployment check can tell
  a missing Android monitor from a missing Windows one.

### 4. `dynamic-sandbox/hooks/stage_integration.py`

13 Android generators added to `MockHookSource`, matching the event shapes the
Frida agent actually emits (including its guest-side pre-computed flags):
benign activity, SMS interception, SMS exfiltration, contact harvest, location
tracking, crypto clipper, clipboard monitoring, audio surveillance, camera
surveillance, accessibility credential theft, banking overlay, tapjacking,
permission escalation, dynamic DEX load, SMS burst.

Stage attribution needed no changes — Android chains flow through
`StageHookMonitor` unmodified, so "the overlay only appeared after the
interaction stage" works the same way it does for Windows injection.

### 5. Tests

`dynamic-sandbox/hooks/test_phase6_android_pipeline.py` — 79 tests:

- **Catalog coverage** — every emitted name resolves, agent and catalog agree,
  MITRE mapping present, SMS bodies stay hash-only, CAPE excludes Android.
- **Ingest/normalization** — events are no longer dropped, URIs classified,
  permissions filtered, call recording distinguished from room audio, string
  numbers coerced.
- **Chains** — all 18 behaviors, supersession, severity, MITRE, evidence.
- **False positives** — ordinary app activity silent; an app's own windows are
  not overlays; accessibility without text capture does not exfiltrate;
  `VOICE_RECOGNITION` is not covert; screen recording is not camera capture;
  an ordinary library load is not a DEX drop; three texts are not a burst.
- **Volume findings**, **scoring**, **stage attribution**, **helpers**.

Two stale assertions in `test_hooks.py` (written against the original
19-API surface, one already failing before this work) were updated to be
platform-aware.

## Data model

Android events use the existing `ApiCallEvent` shape. Example, normalized:

```json
{
  "call_id": "…", "analysis_id": "…",
  "api_name": "OverlayWindowAdded",
  "raw_name": "OverlayWindowAdded",
  "module": "android.view.WindowManagerImpl",
  "timestamp": "2026-01-01T12:00:03.140000",
  "pid": 4242, "tid": 1,
  "args": {"windowType": 2038, "flags": 24, "isOverlay": true,
           "invisibleTapLogger": true},
  "decoded_args": {"window_type_name": "TYPE_APPLICATION_OVERLAY",
                   "is_overlay": true, "invisible_tap_logger": true},
  "category": "overlay",
  "baseline_risk": "high",
  "mitre": ["T1417.002", "T1516"],
  "stage_id": "interaction"
}
```

A matched chain:

```json
{
  "rule_id": "android_targeted_overlay",
  "name": "Fake screen drawn over the app in the foreground",
  "severity": "critical",
  "api_sequence": ["AccessibilityEvent", "OverlayWindowAdded"],
  "mitre": ["T1417.002", "T1516"],
  "stage_id": "interaction",
  "evidence": {"observed_packages": ["com.bank.example"],
               "window_type": "TYPE_APPLICATION_OVERLAY"}
}
```

code at runtime).

## Privacy

Nothing new leaves the guest. Message bodies remain `hash_only`, clipboard and
accessibility *contents* are never transmitted — only the guest's boolean
verdict about them (`possibleCryptoAddress`, `sensitiveSearch`), which is why
those conditions accept the guest flag as a fallback. Recipient numbers,
package names and content URIs *are* recorded: those are the IOCs the report
exists to name.
